# Native iOS (then Android) Scorekeeper: plan

Status: plan only, no code changed. Written against web v22.43 (2026-11-18).

## TL;DR

- **Build a native SwiftUI iPhone + iPad app first, then a native Jetpack Compose Android app.** Both live in this repo next to the web app (`ios/`, `android/`). The web app stays the product of record and keeps shipping.
- **Same features and layout as the web app, except the FAQ, the guided tour and XLSX export.** The iOS app has no FAQ site link-out, no "Take Tour" prompts, no first-run tutorial, and no XLSX. PDF export and the `.json` save stay. See [Out of scope](#out-of-scope).
- **The `.json` save file is one shared format.** A game saved on the web opens on iOS and Android, and the reverse. This is a hard requirement and gets its own section, [Shared JSON contract](#shared-json-contract). Everything else bends around it.
- **Pure Swift/SwiftUI, no cross-platform UI layer.** Scoring rules are ported to Swift (and later Kotlin), not shared as compiled code. Correctness comes from **golden fixtures generated by the real JS** and run in every platform's test suite. The web app stays the source of truth.
- **Biggest risk: parity drift.** The web app ships several version bumps a day. Mitigation is a parity ledger plus the golden fixtures (see [Keeping up with the web app](#keeping-up-with-the-web-app)).

## What the web app is (what we are matching)

Plain HTML/CSS/JS, no build step, global scope. One `gameState` object, mutated by handlers, then `autosave()` and a full `renderAll()`. Modules worth porting, by size:

| Web file | Job | Native counterpart |
|---|---|---|
| `js/scoring.js` (~26 KB) | Pure rules: wagers, totals, ranking, tiebreaks, modes, `migrateState` | `ScorekeeperCore` Swift package (no UI imports) |
| `js/storage.js` | Autosave, 10 rolling backups, save/load `.json`, import names/host, prefs | `Persistence` layer in the same package |
| `js/app.js` (~170 KB) | Rendering, handlers, settings, startup | SwiftUI views + `@Observable` store |
| `js/craft-prize.js` | Craft Prize draw, drumroll Web Audio | `AVAudioEngine` service + draw view |
| `js/question-timer.js` | 1-15 min countdown widget | Timer service + widget view |
| `js/export.js` (~52 KB) | PDF export (and XLSX, which native skips) | PDF exporter, see [Exports](#exports) |
| `js/data/xlsx-templates.js` | Bundled XLSX template | **Not ported** (no XLSX on native) |
| `js/team-audit.js` | Per-team report modal | Team Report sheet |
| `js/host-tools.js` | Shortcuts, progress chart, backups dialog | Hardware-keyboard commands, Swift Charts, backups sheet |
| `js/tutorial*.js`, `faq/` | Tour and FAQ | **Not ported** |

Game modes (`gameState.meta.mode`): `regular`, `theme`, `tune`, `rivals`. Mode helpers (`gameMode()`, `isTune()`, `hasQ5Wagers()`, `roundCount()`, `roundWagerType()`, `wagerMax()`, `guessLimit()`) must be ported with identical outputs. Switching mode wipes the board (keeps Event Details and team names) after a warning; keep that rule.

## Out of scope

Per the request: **no FAQ, no tour and no XLSX export on iOS.** PDF export stays.

- **No XLSX.** Do not port the XLSX half of `js/export.js` (`trivInjectXlsx` and friends) or `js/data/xlsx-templates.js`, and add no XLSX library. Web keeps its XLSX export; iOS offers PDF plus the `.json` save. The Export/Share UI shows PDF and JSON only.

- Do not port `faq/`, `js/tutorial.js`, `js/tutorial-firstrun.js`, `css/tutorial.css`.
- Remove every entry point to them: Settings "Take Tour", the first-run tutorial prompt, the "Try Example" prompts that offer a tour, and any FAQ link.
- Keep **Try Example** (loading the bundled sample game) only if it is useful without the tour; decide in Phase 2. The sample is already a valid save file, so it is cheap.
- Settings > "What's new" is not asked for either way. Default: skip on iOS, revisit later.
- Android: the requests only named iOS. **Assumption: Android skips the FAQ, tour and XLSX too.** Confirm before the Android phase.
- Also out: the Electron desktop wrapper (`desktop/`). It stays as it is. Native apps replace it only for phones/tablets.

## Shared JSON contract

### What the web actually writes today

Verified in `js/storage.js`:

- **Save file** = `JSON.stringify(gameState, null, 2)`, downloaded as `<name>-save.json` (`saveToFile`). It is the raw in-memory state. There is **no `schemaVersion` and no app version inside it.**
- **Load** = `JSON.parse` then `migrateState(data)` (`js/scoring.js`). Migration is *shape patching*, not version numbers: it fills missing fields, clamps strings to `FIELD_MAX`, coerces unknown `meta.mode` to `regular`, pads `rounds` to 4, and so on. That is why old files still load.
- **Autosave** writes the same JSON to key `trivRev6_session`. Backups (`trivRev6_backups`, last 10) wrap the same state. Prefs (`trivRev6_prefs`) are a separate JSON, and the web can already export/import a prefs file.
- **Shape quirks the native models must respect:**
  - Per-team data is **sparse objects keyed by team index** (JSON object keys are strings): `rounds[ri].questions[qi]["3"] = { wager, correct }` or `{ place }` for Rivals; `rounds[ri].bonus["3"]`; `halftime`, `finalWager`, `wager1`, `wager3` all keyed the same way, each value like `{ wager, correct }`. Re-tapping deletes the key, so absent means "not answered".
  - `teams[]` fields: `name`, `scoreGuess` (a **string**), `bonusItem`, `njcb`, `paused`, `adjustment`, `craftPrize`.
  - `meta`: `date` (ISO `yyyy-mm-dd`), `location`, `quizId`, `hostName`, `craftPartner`, `craftPartnerTown`, `bonusItem`, `staffNames`, `themeName`, `mode`, `excludeTopN`, plus legacy `giftCardCount`.
  - Also top level: `gameStarted`, `craftPrizeWinner` (`{ ti, script }` or null), `craftPrizeDraws[]`.
- I did not read every handler. **Before writing the Swift models, generate the spec from real data** (fixture step below) instead of trusting this list.

### Rules so a file round-trips between web, iOS and Android

1. **The web format is the format.** Native reads and writes the exact same keys and value types. No renamed keys, no Swift-flavored shape, no wrapper envelope.
2. **Sparse, string-keyed dictionaries stay sparse.** Swift: `[String: Answer]`; Kotlin: `Map<String, Answer>`. Never convert to arrays, never write `null` placeholders, delete the key when cleared (same as `cycleW` / `setPlace`).
3. **Optional everything on read, tolerant like `migrateState`.** Missing or wrong-typed field falls back to the web default instead of failing the whole file. `scoreGuess` may be a string or empty; numbers may arrive as strings.
4. **Preserve unknown keys.** If a newer web build adds a field, a native open/save must not drop it. Keep a `JSONValue` bag of unrecognized keys on each struct (custom `Decodable`/`Encodable`) and write them back. Kotlin equivalent: `kotlinx.serialization` `JsonObject` passthrough. This is what stops a native save from silently stripping web-only data.
5. **Port `migrateState` exactly**, including `FIELD_MAX` clamping, `MAX_TEAMS = 100`, mode coercion, and legacy fields (`giftCardCount` to `excludeTopN`). It also runs on backups, imports and sample games.
6. **Stable output.** Pretty-printed with sorted keys is fine; the web does not care about key order or whitespace.
7. **Additive forward-compat fields (web change too).** Add the optional fields listed in [Fields to add to the JSON now](#fields-to-add-to-the-json-now) in one web release: `schemaVersion`, `savedBy`, `gameId`, `createdAt`/`updatedAt`, `teams[].id`, `ext`. Old web builds should tolerate extra keys (`migrateState` mutates and returns the object; test it). New code uses `schemaVersion` only to *warn* ("saved by a newer app, some data may not show"), never to refuse. This is the only web change the contract needs.
8. **File handling.** Same file extension and UTType (`public.json`). Name pattern `<event>-save.json` so people recognize them. iOS: `fileImporter`/`fileExporter` or a `FileDocument`, Share sheet, AirDrop, Files, iCloud Drive. Android: Storage Access Framework (`ACTION_OPEN_DOCUMENT` / `ACTION_CREATE_DOCUMENT`). Loading a file keeps the web's confirm: "Replace current session?".
9. **Import (names/host/location only)** (`IMPORT_FIELDS`, `importTeamNames`) ports the same way: scores are never imported.
10. **Prefs are not interchangeable by default.** Portable subset only (theme, text size index, density, stripe level, color-vision mode, timer settings, craft settings). Native-only prefs (haptics, keep-screen-awake) go under their own keys and are ignored by the web.

### Fields to add to the JSON now

**Status: implemented in web v22.45** (not committed yet). Shipped: `schemaVersion`, `savedBy`, `gameId`, `createdAt`, `updatedAt`, `ext`, `teams[].id`, `teams[].notes`, `meta.startedAt`, `meta.endedAt`, `meta.timezone`, `meta.locale`, and `teamId` next to the craft prize winner and the legacy draws list. Behavior to match on native:

- `updatedAt` and `savedBy` change only on a real change (an autosave that changes nothing leaves them alone). Loading a file counts as a save in the app that loaded it.
- `startedAt`, `timezone` and `locale` are stamped together the first time a score is entered. `endedAt` is reserved and nothing sets it yet.
- A mode switch keeps `gameId`, `createdAt`, `ext`, and each team's `id` and `notes`, and clears `startedAt`/`endedAt` because the scores are wiped. A fresh game, a team-names import and "Clear session" get a new `gameId`.
- Files from before v22.45 get `gameId`, `createdAt` ("first opened by a build that tracks it") and team ids filled in by `migrateState`. Duplicate team ids are replaced. A `schemaVersion` higher than the app knows is left as is.
- `teams[].notes` is clamped to 500 characters. There is no screen for notes yet.
- Removing a team now makes the craft prize winner follow its team by `teamId`, and clears the winner if that team was the one removed.
- The "do now" table below is the original proposal; the "when the feature is real" table items `meta.startedAt/endedAt/timezone/locale`, `teams[].notes` and the craft `teamId` moved into "done".

The point of adding these now is that **every file saved from here on carries them**, so later features (sync, merge, history, per-device data) never have to guess about files that lack them. All are optional and additive, so older web builds ignore them. Verify with a test that a web build without the code round-trips a file containing them: `migrateState` mutates and returns the same object, and `autosave` stringifies the whole `gameState`, so unknown keys should survive, but that is worth a test, not an assumption.

**Do now (cheap, and only useful if present on every file):**

| Field | Where | Why it matters later |
|---|---|---|
| `schemaVersion` (int, starts at 1) | top level | Lets any app warn "saved by a newer version" instead of silently dropping data. Bump only for shape changes. |
| `savedBy` (string, e.g. `"web v22.45"`, `"ios 1.0"`) | top level | Debugging ("which app wrote this file?") and per-source bug workarounds. Updated on every save. |
| `gameId` (UUID string) | top level | Stable identity for one game night. Lets backups, imports and a future sync recognize "same game" versus "different game with the same date". Never changes after creation; "Replace session" and mode switch keep it, a fresh game makes a new one. |
| `createdAt`, `updatedAt` (ISO 8601 UTC strings) | top level | "Which copy is newer" for a merge or conflict prompt, sort order in a future game list, and ordering of backups without relying on file dates. `updatedAt` changes on every real edit. |
| `teams[].id` (UUID string) | each team | **The most valuable one.** Today a team *is* its array index: scores live in stores keyed `"0"`, `"1"`... and `removeTeamAt` has to reindex `questions`, `bonus`, `wager1`, `wager3`, `halftime` and `finalWager` by hand when a team is deleted. Any future merge, sync, multi-scorekeeper or undo feature needs a stable team identity. Keep the index keys for now; the id sits beside them and is generated by `migrateState` for older files. |
| `ext` (object, default `{}`) | top level | A reserved namespace for data one platform adds that others should carry but not interpret, such as `ext.ios`, `ext.android`, `ext.web`. It stops native-only extras from colliding with a future web key of the same name. All apps must round-trip it untouched. |

**Add when the feature is real (cheap to add later, nothing is lost by waiting):**

| Field | Idea |
|---|---|
| `meta.startedAt`, `meta.endedAt`, `meta.timezone` | Real game timing for a history screen and "how long did a night run". `meta.date` stays the label. |
| `meta.locale` | If exports or spoken scripts ever localize. |
| `teams[].color` or `teams[].notes` | Host notes per team, or a color for the progress chart. Only if you actually want them. |
| `events[]` (append-only log of score changes with `at`, team id, what changed) | Undo, an audit trail, and per-question timing. **Not recommended yet:** it grows the file on every tap and records more than the host may expect. If added, cap its length and make it optional. |
| `craftPrizeWinner.teamId` and `craftPrizeDraws[].teamId` | Today these store a team *index* (`ti`). Once team ids exist, store the id too so a deleted/re-sorted roster cannot leave them pointing at the wrong team. I did not check whether `removeTeamAt` fixes `craftPrizeWinner.ti`; it does not touch it in the lines I read. |
| `meta.customRoundTitles[]` | Only if Name That Tune round titles ever become editable (`TUNE_ROUND_TITLES` is a constant now). |

**Do not add:**

- Any user account, email, device ID or other personal data. The app has no accounts and the privacy answer for the store should stay "data not collected". A file is shared by AirDrop and email; it should not identify a person or device.
- Computed values (totals, ranks). They are derived by the rules, and storing them lets a file disagree with its own scores.
- Prefs (theme, text size). They stay in the separate prefs file.

**Rules for adding any field later:** additive only; never rename or repurpose an existing key; give it a default in `migrateState` (and the Swift/Kotlin ports) so a file without it still loads; add a fixture that has it and one that lacks it; bump `schemaVersion` only if an old reader would misread the file, not for every new optional field.

### How we prove it (the contract tests)

Put a `contract/` folder in the repo:

```
contract/
  fixtures/            real save files: one per mode, edge cases (paused teams, ties, adjustments,
                       100 teams, Beer Round, old-format file, file with unknown keys)
  expected/            for each fixture: per-team round subtotals, grand totals, ranks, final-results rows,
                       progress counts, produced by the real JS
  generate.js          loads the app via tests/helpers/load-app.js (jsdom), runs the real scoring.js,
                       writes expected/*.json
```

- `generate.js` reuses the repo's existing jsdom harness (`tests/helpers/load-app.js`), so the oracle is the actual web code, not a re-reading of it.
- iOS (Swift Testing / XCTest) and Android (JUnit) load every fixture, run the ported scoring, and assert equality with `expected/`.
- **Round-trip tests:** (a) web fixture -> native decode -> encode -> web `migrateState` -> same totals; (b) native-written file -> web loads in jsdom -> same totals; (c) unknown-key fixture survives native save byte-for-byte in those keys.
- Add a CI job that fails if `expected/` is stale versus `scoring.js` (regenerate and `git diff --exit-code`). That makes any scoring change on the web force a fixture update, which forces native to catch up.

## Architecture (iOS)

### Targets and layout

```
ios/
  Scorekeeper.xcodeproj
  Packages/ScorekeeperCore/     Swift package, no UIKit/SwiftUI: models, migrate, scoring, ranking,
                                persistence, PDF data side. Builds and tests on macOS CLI.
  Scorekeeper/                  App target: SwiftUI views, audio, timer, share/import UI
  ScorekeeperTests/             fixtures from ../contract
android/                        later, same contract
contract/                       shared fixtures (above)
```

Putting rules in a UI-free Swift package makes the contract tests fast (`swift test`, no simulator) and keeps the scoring port reviewable against `scoring.js` function by function.

### State and persistence

- One `@Observable` `GameStore` owns the `GameState` struct (Codable, mirrors the JSON). Views read it; handlers call methods that mirror web handlers (`cycleW`, `setPlace`, `setHW`...), each guarded by `canScore()` exactly as on the web. This is the same loop as the web: handler, mutate, autosave, re-render, but SwiftUI diffing replaces `renderAll()`.
- **Persist as a JSON file in Application Support, not SwiftData.** The save file *is* the interchange format and must stay byte-compatible, so storing the same JSON avoids a mapping layer and a migration system that could disagree with `migrateState`. Apple's own guidance (WWDC26) is that `.codable` attributes are an escape hatch for types you do not own and that your own types should be real models, but the web contract forces a document, and the sources say JSON files fit self-contained documents. Cited below.
- Autosave: debounce a few hundred ms, skip the write when encoded bytes are unchanged (same trick as `persistGameStateNow`), write atomically. Keep the web's last-10 backups (snapshot when a question finishes scoring, plus every 3 minutes) as files in a `Backups/` folder. Resume banner on launch when a session exists.
- Prefs: `@AppStorage`/`UserDefaults` for small preferences. Do not JSON-encode arrays into `@AppStorage`.
- Scores are derived, so cache per mutation in the store (the web's `withScoreMemo` does this per render). 100 teams x 4 rounds is small, but ranking is recomputed constantly.
- Minimum iOS: **iOS 17** (needed for `@Observable`; web claims iOS 12.2+ but native has no reason to go that far). Open decision, see [Decisions](#decisions-needed-from-you).

### Layout parity

The web has two layouts: **phone** = score sheet with a bottom dock and a "scores peek" strip that opens the scores sidebar; **tablet/desktop** = score sheet on the left with an always-visible scores sidebar on the right.

- Drive it from `horizontalSizeClass` (and width, for iPad Split View/Slide Over), not from device type. Regular width: `HStack` of score sheet + sidebar. Compact: score sheet + dock + peek strip + sheet/drawer.
- **Do not use `NavigationSplitView` for the main screen.** On iPhone it collapses to a push-navigation stack, which is not the web's "peek the scores over the sheet" behavior. Use it, if at all, only for Settings. One of the sources also claims split-view child state is lost on rotation; that is a single unverified GitHub note, so test it rather than assume it. Keeping all state in the `@Observable` store (not in views) sidesteps this.
- Rebuild the design system as SwiftUI tokens from `css/styles.css` custom properties: dark/light, the four mode accent colors, `ROUND_COLORS` (rl-1..rl-4), red-green and blue-yellow color-vision palettes, row density (compact/normal/relaxed), zebra stripe levels. Fonts: bundle Inter and Space Grotesk (the repo already ships `inter-var.woff2` and `space-grotesk-var.woff2`; iOS needs `.ttf`/`.otf` conversions of the same families; check the OFL licenses allow embedding).
- Text size: the web has its own A-/A/A+ setting. Do both: respect Dynamic Type and keep the in-app stepper as a multiplier so layouts match.
- Reuse the web's `js/icons.js` SVGs by converting to SF Symbols where an equivalent exists, otherwise SVG assets in the asset catalog.
- Screenshot-compare against the FAQ screenshots in `faq/screenshots/` (they already exist in light and dark for most screens) as the visual spec. We use them as reference only; the FAQ itself is not shipped.

### Audio (Craft Prize drumroll)

The web policy is strict and must carry over: **never claim the audio session until the host taps a Craft Prize sound button**, and mix over the host's background music instead of ducking it.

- `AVAudioEngine` + `AVAudioPlayerNode`. Reuse the four existing WAVs from `assets/audio/` (`drumroll-start`, `drumroll-loop`, `drumroll-end`, `horn`) as-is. Uncompressed PCM is also what loops cleanly: `scheduleBuffer(..., options: .loops)`; compressed AAC loops show gaps at the seam.
- Audio session: category `.ambient` (or `.playback` with `.mixWithOthers`), and **activate it lazily on first tap**, never at launch.
- **Fade the player's volume to 0 before `stop()`.** Forum reports describe a loud pop when stopping a looped low-frequency WAV; the fade is also what the web's "fade out" setting does. Handle engine restarts after backgrounding (`AVAudioEngineConfigurationChange`, interruptions) since the engine can stop on its own after returning from background.
- Port the draw flow as-is: `craftEligiblePool()` (teams outside the top N, `excludeTopN`), the seconds-on-the-left countdown with a bar that starts full and shrinks left, name flash, spoken script, manual drumroll controls, fade seconds, sound test buttons. Persist `craftPrizeWinner` / `craftPrizeDraws` in the save file, but keep `craftDrawState` transient, as on the web.
- Silent switch/haptics: add light haptics on the drumroll end and horn (new, native-only).

### Question timer

- Store an **end timestamp** and compute remaining time from the clock, as the web does, so it survives throttling and backgrounding. 1-15 minute duration (30 s steps), stepper buttons, pulse, color change as time runs low. State is transient (not saved), same as web.
- Native extras (optional, not in web): keep the screen awake while running (`isIdleTimerDisabled`), a local notification at zero when backgrounded.

### Exports

Native exports are **PDF** (the scoresheet), the **`.json` save**, and the progress chart image. **XLSX is intentionally skipped**, which removes the riskiest port in the earlier draft: the web patches a bundled `.xlsx` template with a ZIP library, and none of that comes over.

- **PDF:** `UIGraphicsPDFRenderer` or SwiftUI `ImageRenderer` to PDF, drawn to match the jsPDF layout in `js/export.js`. Include the shrink-to-fit team column rule (`FIELD_MAX`). Each of the four modes has its own columns.
- Deliver through `ShareLink`/`UIActivityViewController` so files go to Files, AirDrop, Mail, Print.
- Verification: render the PDF for each mode and compare it side by side with the web's PDF; add a smoke test that checks page count and that the team names appear in the PDF text.
- Anyone who needs a spreadsheet saves the `.json` and exports XLSX from the web app. That works because the JSON is shared.
- Progress chart: **Swift Charts** with the same series, presets and picker as `host-tools.js`, plus export as image.

## Android (second, same contract)

- Jetpack Compose UI, Kotlin, `kotlinx.serialization` with `JsonObject` passthrough for unknown keys, StateFlow store mirroring the Swift `GameStore`, JSON file in app storage, SAF for open/save, Media3 or `AudioTrack`/`SoundPool` for drumroll (not researched yet), and a PDF route (`PdfDocument`, not researched yet). No XLSX, same as iOS.
- Reuse `contract/` fixtures unchanged. The Android scoring port must pass the same `expected/` files.
- Compose adaptive layouts (window size classes) map onto the same phone/tablet split as iOS.
- Do the Android research pass (audio, PDF, SAF behavior) at the start of the Android phase, not now.
- **Alternative considered: Kotlin Multiplatform for shared logic.** KMP business-logic sharing with SwiftUI/Compose UI is a legitimate, widely used pattern, and sources report logic-only setups share roughly 30-45% of code. Not chosen as the default because you want Swift as much as possible, scoring is only ~26 KB, and golden fixtures already guard against divergence. Revisit if the two ports start drifting. Compose Multiplatform for iOS is out, since it is not SwiftUI.

## Keeping up with the web app

The web app changes constantly (v22.43 as of now, several bumps a day). Native cannot chase every bump.

- Keep a **parity ledger** at the top of `ios/README.md`: "Ported through web v22.xx". Native releases target a web baseline, not each patch.
- Anything that changes **data shape or scoring** must update the fixtures in the same web commit (CI enforces it). UI-only web tweaks (button size, spacing) can be batched into periodic native catch-ups.
- Version numbers: native gets its own (`1.0`, `1.1`...), plus the "ported through" marker. They are independent of the web `vX.Y` and the FAQ `v1.Z` numbers; the web release bump (`js/app.js`, `version.json`, `docs/CHANGELOG.md`) does not need to touch native.
- New game modes are the highest-cost change: one entry in web `GAME_MODES` is a scoring branch, UI, and PDF columns on every platform. Decide per mode whether native ships it day one.

## Risks

1. **Parity drift** (above). Mitigated by fixtures and the ledger.
2. **Audio session behavior on a real iPad.** Simulator is not enough; test with background music, AirPods, silent switch, and backgrounding mid-drumroll.
3. **Silent data loss through the shared file.** Unknown-key passthrough and tolerant decoding exist to stop it; the unknown-key fixture must stay in CI.
4. **Pixel parity.** The web layout leans on CSS flex/grid and `innerHTML` redraw behavior (see the scroll-anchoring code in `renderLeftBody()`); SwiftUI `List`/`LazyVStack` scroll jumps on large 100-team boards need testing.
5. **Store rules.** Apple may question an app that is "just a website"; here it is a fully native app with offline files, so low risk, but Review Guideline 4.2 is worth reading before submission.
6. **Solo maintenance load** of three codebases. Mitigation: native stays a port, never gets features the web lacks except small platform extras (haptics, keep-awake).
